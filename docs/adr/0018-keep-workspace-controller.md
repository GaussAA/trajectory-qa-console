# ADR-0018：不拆分 useWorkspaceController

日期：2026-10-24 ｜ 状态：已接受（经评审后否决该重构）

## 背景

2026-10-23 的架构评审把 `useWorkspaceController` 列为「深化候选③」：465 行、
导出 22 个 action、reducer 有 19 个动作，同时承担 reducer 接线、分析器调度、
持久化、遥测、导出、变体与 toast。提议是把它拆成「分析调度模块」与
「持久化副作用模块」，让 hook 只做组合。

评审当时给的理由是：**横切关注点（取消语义、并发守卫）需要「唯一该改的
地方」，而当时没有答案**——导入的取消只中止当前文件、两批并发会交错
dispatch，正是因为没人说得清这类守卫该落在哪。

## 决定

**不拆。** 该 hook 保持现状，只在其内部修补。

## 理由

1. **提出拆分的那条理由已经不成立。** 取消语义（整批共用一个
   `AbortController`）与并发守卫（批次序号 `generationRef` + loading 期间
   拒绝投放）已在 2026-10-23 就地修好，且落点明确——就在 `ingest` 里，
   也就是「一次导入的生命周期」所在处。这恰恰说明现有结构**能**回答
   「守卫该放哪」，只是此前没被问过。

2. **拆出来的两个模块各自只有一个调用方，是假接缝。** 按本项目的设计
   词汇：一个 adapter 意味着假 seam，两个才是真的。分析调度与持久化副作用
   拆出去之后，唯一的使用者仍是这个 hook——复杂度没有集中，只是搬了家，
   还多了一层要学的接口。删除测试通不过：删掉它们，复杂度会回到 hook 里，
   而不是消失。

3. **规模不是摩擦。** 465 行 / 22 个导出听起来大，但每个 action 都是
   `dispatch` 加一句遥测或 toast，读起来是平的：要找一个行为，直接搜动作
   名即可。真正会咬人的「深层嵌套状态机」这里并没有。用行数当重构理由，
   会把一个可读的文件换成三个互相找不着的文件。

4. **它当前承担的每一件事都是「一次工作区操作」的一部分。** 分析要发
   遥测、成功要落盘、失败要给 toast——这三件事天然属于同一次动作，拆开
   反而要在调用方重新拼回来。

## 已知边界（不因此推翻本决定）

- `stateRef.current = state` 是渲染期赋值，不符合 React 规范。保留。
  改成 `useEffect` 会引入更实际的风险：`dispatch` 之后紧跟着读
  `stateRef` 的回调会读到旧值。这是用真实时序风险去换理论规范，不划算。
  若将来真的出现 StrictMode 下的重复副作用，再针对那一个症状修。
- reducer 的动作集合仍会随功能增长。可接受门槛：**当两个以上调用方需要
  同一组动作时**，就该提取模块了——那时接缝才是真的。目前没有。

## 后续若重新提起

请先回答：拆出去的模块有几个调用方？若答案仍是「一个（这个 hook）」，
本 ADR 依然成立，不必重复讨论。
