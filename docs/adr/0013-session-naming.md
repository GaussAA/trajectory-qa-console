# ADR-0013 会话命名：按 trajectory.id 存，名字跟着轨迹走

- 状态：已采纳
- 日期：2026-10-22

## 背景

真实项目里轨迹文件名是时间戳或流水号，列表里四条并排时，人根本认不出哪条是
「改 prompt 前」、哪条是「加了检索后」。改名本身不难，难的是**改名存哪儿**：
session.id 是「批次前缀 + 序号 + 轨迹 id」拼出来的，每次导入都会变。

## 决定

1. **按 `trajectory.id` 存，不按 session.id。** 轨迹 id 由内容与来源推导，同一份文件
   重新导入仍是同一个 id——与人工标注用的是同一条依据。于是重新打开工具，名字还在。
2. **名称与备注是两个字段，同一条记录。** `{ trajectoryId, name, note }`；
   空名称 + 空备注等于「恢复原名」，reducer 顺手把记录删掉，不留空壳。
3. **名字是展示层的事实，不是数据的改写。** 不改 `trajectory.label`，而是在展示与
   报告组装时取 `labelOf()`。原始文件名永远可查（`title` 与诊断里都保留）。
4. **名字要贯穿到结论里。** 会话列表、评分面板标题、对比视图的下拉、导出的
   Markdown/JSON 报告都使用同一个名字。报告里改名的轨迹用 `{...trajectory, label}` 克隆，
   不污染工作区对象。
5. **备注占第二行，元信息进 `title`。** 列表宽度只有 258px，三行会挤；把「步数 / token /
   分数」放进悬浮提示，信息不丢，密度不变。

## 取舍

- 为什么不把名字写进轨迹对象：轨迹是解析产物，应保持与输入一致；把它当可变状态，
  对比、报告、diff 都会出现两种「事实」。
- 为什么不做批量重命名：当前没有「批量选中」这个概念，先做单条；批量需要另一套选择模型。
- 为什么备注不做富文本：备注的用途是「一句话说明这是哪一版」，富文本是负担。
- 已知边界：名字不进 CLI（命令行没有工作区），`--compare` 仍用文件名。

## 后果

- `SessionNote` 进模型；持久化新增 `tqa.session-notes` 键（同一 schemaVersion 信封，
  坏记录逐条丢弃，不影响其它数据）。
- 工作区新增 `notes` 状态与 `note/set`、`note/clear` 动作；`labelOf` / `noteOf` 是纯函数。
- 列表项结构由「一个按钮」改为「行容器 + 按钮 + 编辑按钮 + 内联表单」，
  双击条目同样进入编辑（键盘用户走编辑按钮的 `aria-expanded`）。
- 测试：工作区 3 项、持久化 1 项（含坏记录过滤）、报告 1 项（改名进 Markdown）、
  App 交互 2 项（改名生效 / 清空恢复原名）。
- 静置状态截图与上一轮逐字节一致：新控件默认 `opacity: 0`，不打扰既有版面。
