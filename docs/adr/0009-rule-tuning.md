# ADR-0009 规则调参：真跑一遍，不做估算

- 状态：已采纳
- 日期：2026-10-22

## 背景

规则包是一份 JSON，改阈值原本只能「改 → 应用 → 看问题清单 → 再改」。一次调参要
三轮，且只能看到当前这一条轨迹。要做的是把这个循环压成一次：动一下阈值，
命中数与分数立刻跟着变。

## 决定

1. **试跑就是真跑。** 调参面板拿草稿包对**所有已载入轨迹**重新执行 `runRules`，
   不是抽样、不是线性外推。代价可控：三条示例轨迹、24 条规则，整个试跑约 5ms。
2. **「禁用后能涨多少分」用同一套评分函数算。** 把该规则的 findings 过滤掉，
   再调一次 `scoreTrajectory`，差值即影响。绝不另写一份「扣分公式」——那必然会
   和真实评分漂移。
3. **阈值就是表达式里的数字字面量。** `numericLiterals` 只认真正的数字常量，
   跳过字符串与标识符（`role == "gpt4"` 里的 `4` 不算）；`replaceLiteral` 在替换后
   重新编译表达式，编译不过就返回 `null`，界面原地回弹并提示，绝不写坏草稿。
4. **草稿与已应用分离。** 调参只改草稿 JSON，仍要按「校验并应用」才生效。
   试错不留痕，应用仍走原来的包校验与持久化。
5. **重算用 `useDeferredValue`。** 十万步轨迹下逐键全量重跑会卡输入框；
   deferred 让输入始终跟手，重算在后台追。

## 取舍

- 为什么不给每条规则做一个滑块：阈值语义千差万别（步数、比例、毫秒、字符数），
  统一滑块会给出误导性的量纲。数字输入框更诚实。
- 为什么不把试跑结果写回问题清单：试跑是草稿推演，写回会产生「界面显示的分数
  和已保存的包不一致」的错觉。清单只反映已应用的包。
- 为什么排序按命中数：调参时真正想知道的是「哪条规则在咬我的数据」，零命中的
  规则排后面，看与不看都不影响判断。

## 后果

- 抽屉里新增「试跑与调参」面板：每条规则的命中数、禁用后平均涨幅、可编辑的数字阈值。
- 单测 10 项（字面量识别、原位替换、编译护栏、试跑统计）+ 组件测试 4 项
  （真命中、改阈值后重算并回写草稿、英文、无轨迹时的空态）。
- 已知边界：试跑只看**规则**，不含人工标注；标注仍按已应用工作区计入界面评分。
- 性能护栏：面板里所有重算都在渲染期做，未引入 worker；若日后单次试跑超过 50ms，
  应把它挪进 `analyzer` 端口而不是继续加缓存。
