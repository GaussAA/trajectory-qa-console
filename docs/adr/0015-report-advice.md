# ADR-0015 报告建议段：只为能说清「怎么改」的规则写

- 状态：已采纳
- 日期：2026-10-22

## 背景

报告此前只回答「哪里不对」。读者看完仍要自己翻译成动作：`exec-dead-loop` 意味着什么？
该改 prompt、改工具，还是改循环控制？把这一步做掉，报告才从诊断变成处方。

风险同样明确：**建议段最容易变成套话**。「请注意优化提示词」「建议提升稳定性」这类
句子除了占版面毫无用处，还会稀释真正有价值的那几条。

## 决定

1. **只为有明确动作的规则写建议**，共 28 条（24 条内置 + 5 类语义判定，其中一条合并）。
   没有映射的规则**不出条目**，不做「通用建议」兜底。
2. **同一规则只出一次，按严重度 → 次数排序**，最多 6 条。读者要的是「先修哪个」，
   不是穷举。
3. **建议文本走 i18n（`advice.<ruleId>`），不进规则包。** 建议是「我们对这条规则的
   判断」，换规则包不该改变「死循环怎么修」；而规则包里的 `title` / `message`
   描述的是「发生了什么」，属数据。
4. **≥2 次才标次数。** 只出现一次就写「1 处」是纯噪音。
5. **对比报告只对「对照新增」的问题给建议。** 基准里已修过的东西不必再提。

## 取舍

- 为什么不做「按维度给建议」：维度级建议必然抽象（「提升结构合法性」），
  抽象即套话。规则级才能落到动作。
- 为什么不做「按 LLM 生成建议」：成本、延迟、不稳定，且与语义复核重复；
  固定映射的可预测性在这里更值钱。
- 为什么上限是 6：超过 6 条时读者不会逐条执行，等于没读。
- 已知边界：建议是通用最佳实践，不含项目上下文（例如「你的工具 X 没有超时」）；
  要项目级建议，得靠人工标注或语义复核。

## 后果

- `core/rules/advice.ts`：`buildAdvice(findings, locale, limit)` 与 `adviceFor`，纯函数。
- 逐会话报告在「问题清单」后追加 `### 建议`；对比报告在「问题变化」后追加
  `### 对照改进建议`。
- 8 项单测：分组计数、排序、严重度升级、无映射跳过、忽略人工标注、上限与并列稳定、
  双语、语义规则 id。
- 报告测试补两条断言：建议段存在且措辞正确、单次命中不标「1 处」。
