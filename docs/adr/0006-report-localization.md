# ADR-0006 报告本地化的三条边界

- 状态：已采纳
- 日期：2026-10-22

## 背景

界面已双语，但导出的报告仍是写死的中文。报告有两个消费方：
人（Markdown，贴进 issue 或周报）与机器（JSON，接 CI 做门禁）。
两者对「翻译」的诉求完全不同——人要看母语，机器要字段稳定。

## 决定

1. **Markdown 全量本地化。** 标题、表头、维度名、等级、结论、时间格式
   都按当前 locale 输出（`formatDateTime` 用 `zh-CN` / `en-US` 的 Intl 标签）。
2. **JSON 只译「值」，不译「键」。** 键名是消费方契约，`score`、`dimensions`、
   `findings` 永远不变；`gradeLabel` 与维度 `label` 随语言变化，另加顶层
   `locale` 字段声明本次导出的语言。CI 不会因为用户切了语言而解析失败。
3. **规则包文本不翻译。** 规则标题与提示是**数据**，随包走，不随界面走；
   要英文结论就导入英文规则包。同理，规则包 `name` 在报告里保持原样。

## 取舍

- 为什么不给 JSON 做双份键（如 `score` / `得分`）：一套键是契约，两套键会在
  半年内分裂成两个事实。
- 为什么不让报告层自己读 `navigator.language`：报告必须与**用户所见界面**一致，
  语言是显式入参（`locale`），不从环境猜。
- 为什么把 i18n 拆成 `core.ts` + `index.tsx`：报告是纯函数层，不应为了取一句
  文案而依赖 React；`core.ts` 无组件依赖，Node 侧（未来 CLI）可直接复用。

## 后果

- `buildMarkdownReport` / `buildJsonReport` 的 `locale` 为**必填**参数，漏传即
  编译失败——这次改造正是靠这一点一次性找出全部调用点。
- 英文报告里仍会出现中文的规则标题与详情，这是**有意的数据边界**，
  已由测试固定（报告中除规则包名与问题清单外不得出现中文）。
