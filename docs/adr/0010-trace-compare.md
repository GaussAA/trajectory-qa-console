# ADR-0010 轨迹对比：按结构对齐，按内容判变

- 状态：已采纳
- 日期：2026-10-22

## 背景

同一任务改 prompt / 换模型后，两条轨迹要能并排看差异。天然的诱惑是把整条消息文本
当作比较单元——但改 prompt 之后**每一条助手文本都会变**，整条轨迹会变成「全部删除 +
全部新增」，对比就退化成两次独立阅读。

## 决定

1. **对齐看结构，差异看内容。** 结构签名 = `角色 | 工具名序列`；对齐用 LCS 求最长公共
   结构序列，再对每一对匹配检查内容指纹（文本、推理、工具参数、结果的 FNV-1a 哈希）。
   于是「同一个助手回合换了说法」显示为 `内容变化`，而不是删一个加一个。
2. **内容指纹先哈希再比较。** LCS 内层要比较 O(n·m) 对，直接比长字符串会让大轨迹卡死；
   32 位 FNV-1a 在进入 LCS 前就把每个步骤压成 4 个整数。
3. **超过上限就退化，并如实呈现。** `(n+1)(m+1) > 400_000` 时按位置配对，长短差异
   仍然表现为增删。不假装对齐过——宁可粗，不可错。
4. **问题差异按「规则 + 步号 + 文案」三元组判定。** 同一规则命中不同步骤算两条问题，
   否则「把错误从第 2 步挪到第 5 步」会被误判为无变化。
5. **只有一条轨迹时不进对比。** 面板直接提示「至少两条」，不做自己跟自己的零差异对比。

## 取舍

- 为什么不用 Myers：LCS 的 DP 表在这类规模（几百到几千步）已经足够，且更容易解释
  与测试；Myers 的收益要到万级才明显，而万级已经被上限挡住了。
- 为什么对比视图占中右两列而不是新开窗口：左侧会话列表仍是选择器，用户不必来回切。
  抽屉宽度不足以并排显示两列步骤，所以这里破例改了栅格（`.main-grid.compare-mode`）。
- 为什么对比不做编辑：对比是判断「改得好不好」，改是另一件事。可编辑的对比视图会
  立刻滑向「双栏编辑器」，那是另一个产品。

## 后果

- `src/core/compare/sessions.ts`：`compareCards` / `diffFindings` / `alignSteps` / `summarizeAlignment`。
- 单测 11 项覆盖：分数与维度增量、问题三分（新增/修复/仍在）、步号敏感性、
  结构对齐与内容变化、增删步、上限退化、空侧。
- 组件测试 6 项：分数与步骤增量展示、问题变化、状态徽标、双向切换、英文、单轨迹提示。
- 已知边界：对比不包含人工标注（标注属于工作区状态）；步骤差异最多展示前 80 条。
