# ADR-0007 CLI 入口：共用 core，三层失败词汇，退出码即契约

- 状态：已采纳
- 日期：2026-10-22

## 背景

工具最初只有界面。要接进 CI 门禁、要审一整个目录的轨迹，就需要一条命令：
`trajectory-qa ./traces --fail-below 80`。难点不在读文件，而在**不把 UI 的逻辑
复制一份**——复制出来的第二套判分口径，半年后必然和界面不一致。

## 决定

1. **只复用，不复制。** CLI 走 `analyze()` → `scoreSession()` → `buildMarkdownReport()`，
   与界面同一条链路、同一份规则包、同一套评分。CLI 自己只新增「遍历目录、
   汇总表格、退出码」三件事。
2. **失败词汇分三层，各管一段：**
   - `UsageErrorCode`（args）：选项写错；
   - `CollectErrorCode`（collect）：路径不存在 / 没有轨迹 / 文件过多；
   - `AppError`（core）：单文件解析或分析失败，属于**结果**而不是崩溃。
   三者的边界正好对应「参数 → 文件系统 → 内容」，不互相借用。
3. **退出码是契约。** `0` 通过、`1` 门禁未通过、`2` 用法/读写/无可分析内容。
   没有可分析内容时**必须是 2**：空跑报成功，等于让 CI 永远绿。
4. **产物自包含。** `vite build --config vite.cli.config.ts` 把 CLI 与 core 打成一个
   `dist-cli/qa.mjs`（只外置 `node:*`），运行时不需要 `node_modules`。
5. **进程边界单独一层。** `bin.ts` 只做 argv/退出码/未捕获异常；`main.ts` 不写
   `process.exitCode`，因此可以被测试和其他工具直接 import。

## 取舍

- 为什么不直接用 `tsx` 跑源码：CI 与用户机器会多一个运行时依赖，而且「打出来的
  那个文件」从未被验证过。现在是构建产物冒烟（`scripts/smoke-cli.mjs`）。
- 为什么目录扫描**超限即失败**而不是截断：门禁少扫一批文件比门禁报错更危险。
- 为什么路径统一用 `/`：Windows 与 POSIX 的报告才能逐字节比对。
- 为什么 CJS 不做：`node>=22` + ESM 足够，少一套构建矩阵。

## 踩到的坑

Vite 的 SSR 构建默认把 `dependencies` 外置，第一次打出来的 `qa.mjs` 顶部还写着
`import { z } from "zod"`——拷到别处就跑不起来。冒烟脚本里那条「除 `node:` 外不得有
裸模块名」的断言把它逮住了，随后用 `ssr.noExternal: true` 强制内联，产物 116 KB → 288 KB。

## 后果

- 界面与 CLI 的行为一致性由同一套 187 项测试按住；CLI 另加 53 项单测与 11 项冒烟断言。
- 规则包、语言、门禁阈值都成了命令行参数，CI 里可以直接按项目调口径。
- 已知边界：CLI 不带人工标注（标注只存在于界面工作区），因此同一份轨迹在两边
  可能差一个人工标注的分数。
